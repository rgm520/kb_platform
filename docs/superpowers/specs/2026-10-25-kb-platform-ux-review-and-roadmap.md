# 企业知识平台 2.0：用户体验评估与演进路线图

> 日期：2026-10-25（第 1 版，含自查修订）　｜　对象：平台决策者　｜　数据口径：本机生产库 `kb/data/kb.db` + 运行中服务实测
> 一句话结论：**平台已经"能用了"，但离"每天都用"还差三件事——搜得到但答不准、文件只能看不能理、平台自己不可观测。**
> 其中最贵的不是缺功能，而是**用户搜不准却不会告诉你**：平台没有任何反馈通道，所有"不准"都是静默的。

---

## 0. 一页纸结论（TL;DR）

| # | 结论 | 一句话证据 |
|---|---|---|
| 1 | 底子比想象中好，**不是"功能不够"，是"最后一公里没打磨"** | 76 个接口 / 8 个页面 / 4 路召回 + RRF 融合 / 395 个自动化用例，1.0 时代该有的都有 |
| 2 | **最大的用户体感问题在"答"不在"搜"** | 检索只有 RRF 融合，**无重排、无查询改写、无意图识别**；且全文检索在 Web 端**没有入口**（后端能力已存在） |
| 3 | **"问不准"是静默的**——没有反馈按钮，也没有检索调试视图 | 没有任何"这个答案没用"的记录通道；现有审计数据多为历史测试流量，**不能当使用基线** |
| 4 | **看板 89% 的统计是平台自己的内部文件** | "已跳过 126"里 **113 条**是平台导出的 `_kb\wiki\entities\*.md`；真实与用户有关的只有 13 篇扫描件；且 `_kb` 目录**直接出现在用户文件树里**，还占着 20% 的解析队列 |
| 5 | **一个静默的检索黑洞**：4 篇文档的向量全丢，块还在库 | embedding **单次输入上限 2,048 token**，一篇里有一个超限块就整篇向量作废；这 4 篇共 126 个块**永远搜不到**，且失败只写在管理员才看得到的字段里 |
| 6 | **一个必须尽快堵上的越权口子**：人工校正层（wiki）的召回通道**完全没有做目录授权过滤** | 现在 0 行数据所以无害；一旦按计划给校正层做 UI，这就是越权泄露路径 |
| 7 | 知识图谱是**最后才可用**的功能 | Tier2 提炼 83/677（12.3%），572 个任务排队中；这期间图谱页"已进入知识图谱"= 0，用户第一次打开会觉得"图谱是空的" |

**最该马上做的三件事（合计约 1 周，见 §5 阶段 0）**

1. **把"答不准"变成可见**：答案页加「不准 / 换个说法再问 / 引用不对」三个按钮 + 一个检索轨迹面板（看这次召回了什么、被哪路压下去）。
2. **清掉 1 个统计噪音 + 1 个真黑洞 + 1 个队列浪费**：`_kb` 内部目录从文件树/统计/队列里剔出去（顺带清掉 113 条脏行与 113 个白排队的任务）、修掉 embedding 2,048 token 超限、把"为什么没解析成功"对普通用户可见。
3. **把全文搜索接到文件页**：后端已经能搜正文，Web 端却没入口——这是**当天就能白捡的体验提升**（注意：agent 工具链已经在用它，只是 Web 用户用不到）。

## 2. 从用户视角看到的痛点

> 排序按"痛感强度 × 影响人数"。每条给出：现象 → 数据 → 用户会怎么说 → 根因位置。

### 2.1 【最痛】搜得到但答不准：检索没有"最后一道把关"

- **现象**：搜"立项请示"能搜到一堆"立项"，但不一定是他要的那份；问"XX 项目的立项请示在哪"，答案里的引用片段常常答非所问。
- **数据**：检索层是 4 路召回 + RRF 融合（`kbplatform/retrieval.py:144-213`），**没有重排、没有查询改写、没有意图识别**（全库 grep `rerank` / `rewrite` / `intent` 零命中）。
- **用户会怎么说**："我问的是 A，它给我 B。"→ 一次答不准，用户就再也不问了。
- **连带问题**：答案引用**没有可信度分数**（`citations` 里没有 score 字段），用户无法判断该信哪一条。

### 2.2 【最痛】"答不准"是静默的：平台不知道自己哪里不行

- **现象**：用户不满意就走了，平台一点信号都没有。
- **数据**：问答接口返回 `answer + citations`，**没有任何反馈入口**；审计只记"谁问了什么"，不记"答得对不对"；`model_usage` 表**建好了但从不写**（`kbplatform/db.py:278-287`）。
- **必须澄清的一点**：现有 237 条审计**不是使用基线**——其中 66 条的 user_id 属于已删除的历史账号（多为一次性测试密钥），43 条 user_id 为空（`reason=prefix/unknown` 的 token 鉴权失败记录，来自探针脚本），真正能归因到在册 3 个账号的只有 128 条，且大部分还是开发期自测。
- **用户会怎么说**：（不会说）——这正是问题：决策者会以为"问答没人用"，实际很可能是"用了但不准，然后默默不来了"。
- **为什么这条排第一**：后面所有 AI 投入都要靠它来定优先级。没有反馈，做完了也不知道该继续优化重排还是改块长。

### 2.3 答完就断：没有追问、没有历史、没有流式

- **现象**：问完一句想接着问"那它的工期呢"，系统完全不知道"它"是谁；答案要等模型跑完才出现，等几十秒没进度。
- **数据**：`QueryReq` 只有 4 个字段（question/model/top_k/include_text，`service.py:77-81`），**Web 端每次问答独立检索**；库表里没有 Web 会话/历史表（飞书侧有 `feishu_sessions`，多轮上下文在 opencode 服务侧托管）；模型调用写死 `"stream": False`（`models.py:208,243`）。
- **用户会怎么说**："每次都得把上下文重新打一遍。"

### 2.4 台账是脏的：看板 89% 的"跳过"是平台自己的内部文件

- **现象**：看板显示"已跳过 126"，用户以为自己的文件没解析成功；文件浏览里还多出一个看不懂的 `_kb` 文件夹，里面是 113 个"实体名.md"。
- **数据**（本次实测确认）：
  - 126 条 skipped 中 **113 条**路径形如 `AI知识库\_kb\wiki\entities\*.md`——这是 **1.0 引擎导出的 wiki 实体文件**，属于平台自己的产物；
  - 抽查其中 40 条，**文件在 NAS 上全部真实存在**（`os.path.exists` = 40/40），所以"源文件已删除"这个文案本身就是错的；
  - **两个扫描器行为不一致**：1.0 的 `kbplatform/catalog.py:18-22` 会跳过 `_kb`，2.0 的 `kbplatform/fsindex.py:16-17` **不跳过** → 平台自己的文件被扫进 `catalog`/`fs_entries`/统计、并出现在用户文件树里；
  - "源文件已删除"文案的真正来源是另一条路径：1.0 流水线用**整张 catalog 表**预热监控快照（`pipeline.py:45-48`），每次重启就把这 113 条重新标一遍；
  - **这 113 条还占着 113 个 extract 任务（572 个排队任务里的 20%）** → 解析算力被平台自己的文件吃掉；
  - 真正与用户有关的只有 **13 篇扫描件**。
- **用户会怎么说**："这平台一半文件都是坏的。"

### 2.5 一个静默的检索黑洞：4 篇文档永远搜不到

- **现象**：文档显示"处理失败"，其实正文已经切好了，但搜不到它。
- **数据**：failed 8 篇里 **4 篇**是 `HTTP Error 413`，涉及 `2.某公司安全管理分册（制造厂）`、`1.某公司管理手册（纪检监督管理分册）2023版`、`1.某公司管理手册（财务管理分册）2023版`、`6.《某公司策划创效奖考核兑现管理规定与流程》V3.0`——**恰恰是 3 个管理手册分册，最该被搜到的一批**（大小分别 8.3 / 1.8 / 12.5 / 0.3 MB，合计 23 MB）。这 4 篇共 126 个块在库里，但**一个向量都没有**。
- **根因（比"块太大"更精确）**：embedding 服务对**单次输入**有 **2,048 token 上限**；`indexer.py:168` 把**一篇文件的所有块放进同一次调用**，因此**一个超限块就让整篇的向量全部作废**。实测：3,156 字符的单块单独就失败，而 12 块 / 72,585 字符 / 20,677 token 的整批调用却成功（说明限制是**单输入 token 数**、不是请求体大小）。另外 `indexer.py:169` 的 `if vecs: vs.add(...)` **静默跳过**，无向量也不报错。
- **附带事实**：块长 > 4,000 字符的共有 134 个，但它们**大多数能正常向量化**（135 个文档含 >3,200 字符的块却没失败）——所以"全面调小块长"并不是解药，**"按块嵌入 + 超限单独处理"才是**。
- **用户不会知道**：失败原因写在 `status_detail` 里，**普通用户看不到**（`service.py:670-672`）。

### 2.6 图谱长期空转：最酷的功能最后才可用

- **现象**：用户第一次进"知识图谱"看到空画布，等几小时才有东西。
- **数据**：Tier2 83/677（12.3%），572 个 extract 任务排队；流水线单线程、每 60 秒一轮，OCR 与提炼共用同一个 worker；页面默认只展示 60 个高频节点，而实体节点已有 15,892 个。
- **用户会怎么说**："图谱是空的 / 图谱太乱。"

### 2.7 文件只能看、不能理：整理能力几乎为零

- **现象**：文件页能浏览、预览、搜索、删除、上传，但**不能改名、不能建文件夹、不能移动/复制、不能拖拽、不能收藏、不能记"最近打开"**。
- **数据**：全库无 `dragstart`/`dragover`/重命名/移动/复制接口；右键菜单只有 4 项（预览/下载/复制路径/删除）；列表上的"整理"动作只有**删除**。
- **用户会怎么说**："整理 NAS 上的文件还得回到资源管理器。"→ 直接把用户赶回 Windows 文件管理器，平台就退化成一个"搜索框"。

### 2.8 只会搜文件名，正文搜不了（Web 端）

- **现象**：文件名秒搜很好用（FTS5 trigram，150ms 防抖），但用户记不清文件名、或文件叫"扫描件001.pdf"时，就没辙了。
- **数据**：`POST /api/v1/search`（关键词+向量双路检索、返回 chunk 级结果和召回统计）**在 Web 前端零调用**。需要澄清：这条能力**并非没人用**——agent 工具链（`tools/kbq.py:133`、WorkBuddy 技能包 `scripts/search.py:70`）一直在用，审计里有 73 次检索调用（其中 25 次来自浏览器会话）。所以准确说法是：**能力在、agent 在用、Web 用户用不到**。
- **用户会怎么说**："我知道里面有，但搜不出来。"

### 2.9 只看得见"坏"，看不见"为什么"

- **现象**：普通用户在看板看到"已跳过""处理失败"，点开没有原因。
- **数据**：`catalog.status_detail`（失败原因）对普通用户被主动剥掉（`service.py:670-672`）。
- **用户会怎么说**："它坏了，但没人告诉我怎么坏的，我只能等。"

### 2.10 涉密能力：后端齐、入口缺、且从未被真正验证

- **现象**：管理员在管理台找不到"涉密目录"在哪标；即使标了，也不确定它到底管不管用。
- **数据**：`GET/PUT /api/v1/admin/restricted` 两个接口 + 前端 `adminRestricted()` 函数**都在**，但管理台 6 个页签里没有对应按钮（`web/index.html:247-252`）——功能等于不存在。而库里**已经标了 8 个涉密目录**（党建党务/团委/宣传/工会、审计资料、薪酬福利、涉及审计、整共享），**全都落在当前索引范围之外** → 这套机制在生产里**一次都没被真正触发过**，也没有一条相关回归测试。
- **风险提示**：一旦决定放开索引范围，这些标记会**自动生效**（命中即改走本地模型、原文禁止返回、禁止下载）。所以**管理台入口必须在放开范围之前落地**，否则等于默默改变答案行为。
- **为什么可惜**：涉密是这类平台**最有说服力的差异化能力**，现在只有开发看得见。

### 2.11 人工校正层是空壳（且带一个越权口子）

- **现象**：AI 抽错了知识点，用户改不了；改了也没地方保存。
- **数据**：`wiki_pages` 表 **0 条数据**，且没有 UI。检索层给了它一个 wiki 召回通道，但**该通道完全没有做目录授权过滤**：`retrieval.py:152` 取 wiki 候选，随后 `:155-158` 只过滤关键词/向量的 id、`:166-167` 只过滤图谱的 id，**wiki 候选不在 ACL 过滤范围内**。现在 0 行数据所以无害；一旦按计划给校正层做 UI 并开始写内容，**越权泄露路径立刻成立**。
- **补充澄清**：此前认为"空图层给所有结果加权 1.8×"并不成立——0 行时 `_wiki_ids_for` 直接返回空、没有任何 wiki id 进入 RRF 列表，实际上**没有加权效果**（`retrieval.py:126-129`、`:50`）。
- **用户会怎么说**："它说的不对，可是我改不了。"

### 2.12 平台自己不可观测、不可恢复

| 缺失 | 现状 |
|---|---|
| 备份 | **无任何备份脚本**。索引库损坏 = 索引全丢（文件还在 NAS 上，但要重跑数小时解析） |
| **备份的坑** | `kb.db` **2.25 GB**，而 `kb.db-wal` **2.49 GB**——WAL 比主库还大，说明 checkpoint 饥饿。**直接复制文件做的备份很可能是不可恢复的**，必须用 SQLite 备份 API / `VACUUM INTO` |
| 指标 | 无 `/metrics`、无队列状态 HTTP 接口（`jobs` 表只有流水线自己用）→ 用户和管理员都看不到"排队 572 个任务" |
| 告警 | 无邮件/企微/webhook 通道；看门狗只检查"进程还在吗"，**不检查内容健康** |
| 健康检查 | 只有一个 `/health`（返回文件/块/节点计数），不查模型、不查 NAS、不查队列积压 |
| 日志 | 全部 `mode="a"` 追加，无轮转；流水线上还在持续出现 `database is locked`（哈希任务撞上 Web 写入） |
| 回收站 | `expires_at` 写了但**没有清理任务**，`_kb_trash` 只增不减 |
| **会话稳定性** | Web 会话密钥取 `KB_SESSION_SECRET` 或**每次启动随机生成**（`service.py:185`）→ **平台一重启，所有人当场被登出** |
| **密钥管理** | `config.toml` 里的 `session_secret` 明文写着，但它其实是**加密主密钥**（token 密文 + SMB 密码解密都靠它，`service.py:189`）——**可以改存储方式，但改值会同时废掉所有密钥的明文恢复和 5 个共享的 SMB 认证** |

### 2.13 移动端没有

- **现象**：文件页是桌面交互（表格 + 右键菜单 + Shift 连选），手机上基本没法用。
- **数据**：无响应式专用布局、无触摸手势；实际用户大概率是通过**飞书机器人**而不是网页访问。
- **判断**：不值得为网页做移动端，**但飞书链路应该成为移动端主入口**（该链路有 132 个测试函数，工程上是最成熟的一块）。

### 2.14 同一件事有两套实现（维护性痛点）

| 双份 | 现状 | 后果 |
|---|---|---|
| 授权 | 老 `user_scopes` + 新 `grants`，靠每次启动迁移同步 | 已经出过"文件页空白、看板有数据"的事故（已修） |
| 流水线 | 1.0 `pipeline.py` 全量快照比对 + 2.0 `SourceScanner` 周期扫描 | **两者的跳过名单不一致**（`_kb` 一个跳一个不跳）→ 直接产生 §2.4 的脏数据 |
| 统计 | `bump_stats` 累加 vs `write_non_doc_stats` 覆盖写 | 同上 |
| 扫描范围 | 1.0 按共享根全量、2.0 按配置根 | 10-25 的 12 万文档洪流就是从这里来的（已修） |

## 3. 优化建议（按"要不要动用 AI"分开）

### A 类 · 检索质量（AI，收益最大）

| 建议 | 具体做法 | 成本 | 预期收益 |
|---|---|---|---|
| **A1 答案反馈 + 检索轨迹面板** | 答案页加「👍/👎 + 引用不对 + 换个说法再问」；每次问答持久化一条**精简轨迹**（问题哈希、各路候选 id/名次、融合后分数、ACL 过滤前后数量），管理台可复现；轨迹仅管理员可见、只存 id 不存原文、保留 30 天 | 1.5–2 人日 | **把"不准"变成可度量**，后续所有 AI 投入有靶子 |
| **A2 轻量重排** | 4 路召回后加一层"块级二次打分"（复用 bge-m3 算 query-chunk 余弦相似度 + 标题/路径/时间加权），先取 top-20 再重排取 8 | 1–2 人日 | 命中率提升明显，成本几乎为零；不够再上 `bge-reranker`（+1 模型、+0.5 人日） |
| **A3 查询改写 + 意图路由** | 把口语问题改写成 2–3 个检索式（缩写、同义、时间范围补全）；识别意图（找文件 / 问事实 / 要流程） | 1–2 人日 | "去年那个立项请示"这类问题命中率提升 |
| **A4 引用可信度 + 片段高亮** | 引用显示**真实余弦相似度**（来自 A2，0–1 保留一位小数）+ 命中通道标签 + 原文高亮定位 + "依据 N 条来源" | 0.5–1 人日 | 用户敢信、敢复制。**注意：不要把 RRF 融合分当"相关度"展示**（它的量级是 0.016–0.065，展示成 3% 会误导） |
| **A5 文档级摘要 + 整篇问答** | 每篇文档预生成 200 字摘要 + 章节标题；问答先选文档再选片段；"这份手册讲了什么"能答全 | 2–3 人日（**LLM 批量耗时另计**） | 目前只喂 top-8 片段，长文档必然答不全 |
| **A6 embedding 2,048 token 修复** | **按块单独嵌入**（或只对超限块二次切分），超限块记警告；先救回 4 篇，**全局重切块单独立项**（见 §7 决策点 3） | 0.5–1 人日 | **直接救回 4 篇制度文件** |

### B 类 · 知识治理（半 AI，替管理员省事）

| 建议 | 具体做法 | 成本 | 预期收益 |
|---|---|---|---|
| **B1 内部目录与统计口径清理** | ① 2.0 扫描器跳过 `_kb`；② 流水线预热快照改为只取监控范围内的行；③ 文件树显式隐藏 `_kb` / `_kb_trash`（文件页是实时列目录，跳过名单对它无效，必须单独过滤）；④ 清 113 条脏行 + 113 个白排队任务；⑤ wiki 导出目录搬离被监控的 NAS 根（见 §7 决策点 4） | 1 人日 | 看板从"126 个坏文件"变成"13 篇待 OCR"；**省下 20% 的解析算力** |

| **B6 wiki 通道补 ACL** | wiki 候选纳入同一套目录授权过滤；补一条回归测试（今天没有） | 0.5 人日 | **在做人工校正层 UI 之前必须先做**，否则是越权口子 |

## 4. AI 功能建议与优先级

### 4.1 排序依据

**痛感强度 × 覆盖人数 ÷ 实施成本 × 数据就绪度**。数据就绪度很关键：平台已有 4 路召回、14,060 个知识点节点、15,892 个实体节点、MD5 哈希、算力池——**大量 AI 能力的地基已经打好**，缺的是"接上去"而不是"从零做"。

### 4.2 第一梯队（立刻做：低成本、直接决定满意度）

| # | 能力 | 解决哪个痛点 | 用户看到什么 | 需要什么 | 预估 | 为什么排这里 |
|---|---|---|---|---|---|---|
| 1 | **答案反馈 + 检索轨迹面板** | §2.2 | 答案下方三个按钮；管理员能复现任意一次召回（各路名次、谁把谁压下去了） | 1 张反馈表 + 1 张轨迹表（管理员可见、30 天、只存 id 不存原文） | 1.5–2 人日 | 成本最低、决定后续所有投入方向。**不做这个，后面所有 AI 都是盲飞** |
| 2 | **轻量重排 + 查询改写 + 意图路由** | §2.1 §2.3 | 问同一句话，引用明显更对口 | 复用 bge-m3 + 1 次改写调用 | 2–3 人日 | 用户投诉的**第一原因**；已有 4 路召回做底座，重排是"最后一公里" |
| 3 | **引用可信度 + 原文高亮 + 答案溯源** | §2.1 | 每条引用带真实相似度、答案里的句子能点开对应原文 | 依赖 A2 产出的余弦分；若 A4 要先上线，**只显示命中通道标签、不显示数字** | 0.5–1 人日 | 几乎零成本但**感知提升最大**：从"AI 说的"变成"文档里写的" |
| 4 | **多轮追问 + 会话历史 + 流式输出** | §2.3 | 接着上一句问；答案边生成边出；历史可回看 | 新增 `chat_session` / `chat_message` 两张表；**prompt 只带最近 2–3 轮**；每轮打"是否来自涉密片段"标记，回灌 prompt 前先脱敏 | 3–4 人日 | 真实使用里"追问"占一半；飞书侧已有多轮（session 在 opencode 侧），**Web 侧反而落后** |

### 4.3 第二梯队（价值大，但需要配套流程）

| # | 能力 | 解决哪个痛点 | 用户看到什么 | 预估 | 前置条件 |
|---|---|---|---|---|---|
| 5 | **文档级摘要 + 标签 + 整篇问答** | §2.1 §2.6 | 文档卡片上有一行摘要和 3 个标签；能问"这份手册讲了什么" | 2–3 人日 + LLM 批量耗时（677 篇走算力池，本地+远端各 1 路） | A6 先修；批量任务要有进度可见、不得饿死 Tier2 积压 |
| 6 | **近似重复检测 + 版本差异说明** | §2.4 §B2 | 看板新增"近似重复"组，说明"哪版更新、改了什么" | 2–3 人日 | 感知哈希；差异比对复用算力池 |
| 7 | **答案幻觉核查（逐句回查原文）** | §2.1 §2.2 | 答案里每个关键论断标"有原文依据 / 无依据" | 2–3 人日 | 需要 A4 的片段定位 |
| 8 | **自动归类与规范命名** | §2.7 §B3 | 新文件自动给出"建议放到 X 目录、建议改名 Y"，一键执行 | 2–3 人日 | 目录先验（B5 标签） |
| 9 | **表格 / 图片理解（视觉模型 + 结构化抽取）** | §2.1 | xlsx 里的表格能被问；图纸/照片能被描述 | 3–5 人日 | 90 个 xlsx 目前只取文本，Excel 里的关键信息基本丢着 |

### 4.4 第三梯队（自动化助手，放在治理跑顺之后）

| # | 能力 | 解决哪个痛点 | 预估 |
|---|---|---|---|
| 10 | **平台内 agent 代办**：批量整理/改名/归类、生成目录摘要、给新文件写摘要 | §2.7 §B3 | 5–8 人日（要先做工具调用协议） |
| 11 | **自动简报**：每周"新增 12 篇 / 解析失败 3 篇 / 新增重复 2 组 / 待我确认 5 条"推给管理员 | §2.12 | 1–2 人日（复用飞书推送） |
| 12 | **语义化待办**（从知识库发现"该做还没做的事"） | 需要业务规则，风险高 | 先不做 |

### 4.5 第四梯队（协作沉淀，需要团队真的用起来）

| # | 能力 | 解决哪个痛点 | 预估 |
|---|---|---|---|
| 13 | 收藏 / 最近打开 / 常用目录 | §2.7 | 1–2 人日 |
| 14 | 评论 @ + 订阅变更提醒 | §2.13 | 4–6 人日 |
| 15 | 人工校正闭环（wiki 层 UI + 反馈回流抽取） | §2.11 | 3–5 人日；**必须先做 B6（wiki 通道补 ACL）**；有反馈数据后再做效率高得多 |

### 4.6 明确建议**现在不要做**的事

1. **不要先换更大的模型**：当前瓶颈是"召回与重排"，不是"模型不够聪明"。同一个模型加上重排，效果提升远大于换模型。
2. **不要先做协同编辑**：没有任何证据表明多人同时编辑是刚需。
3. **不要先升级图谱可视化**：图谱现在连数据都没建完（Tier2 12.3%），可视化做得再炫也是空的。
4. **不要现在全量 OCR 存量**：13 篇按 136 秒/页完全可控；但整个共享若还有大量扫描件，**先做重复/价值筛选再决定**，否则会像 10-25 那次一样把算力池打满。
5. **不要把 ≈20 万文件一次性塞进索引**：浏览范围已经够用，解析范围要按"业务价值 + 人工确认"逐步放开（见 §7 决策点 1）。

## 5. 分期路线图

### 阶段 0 · 止血与清账（约 1 周，7–8 人日）

| 交付 | 对应痛点 | 投入 |
|---|---|---|
| `_kb` 内部目录：扫描跳过 + 流水线快照范围修正 + **文件树显式隐藏** + 清 113 条脏行与 113 个排队任务 | §2.4 | 1 |
| 修 embedding 2,048 token：**按块单独嵌入**，先救回 4 篇制度文件；向量缺失要显式告警（不再静默） | §2.5 | 1 |
| 答案反馈三按钮 + 检索轨迹表与管理员面板 | §2.2 | 1.5–2 |
| 文件页接全文搜索（`/api/v1/search` 已有） | §2.8 §C1 | 1 |
| 失败原因对普通用户可见（脱敏）；涉密标记补管理台入口 | §2.9 §2.10 | 1 |
| 可恢复的备份（SQLite 备份 API，7 份）+ WAL 膨胀排查 | §2.12 §D1 | 1 |
| wiki 通道补 ACL + 回归测试（人工校正层 UI 的前置） | §2.11 §B6 | 0.5 |

**阶段 0 结束时的可见变化**：用户第一次打开看板不会再看到"126 个坏文件"；4 个管理手册能被搜到；文件页能搜正文；平台开始知道"哪里不准"；索引有可恢复的备份。

### 阶段 1 · 把"准"做出来（约 2 周，8–10 人日）

轻量重排 →（不够再上 bge-reranker）→ 查询改写与意图路由 → 引用可信度与原文高亮 → 文档级摘要与标签 → 多轮追问 + 会话历史 + 流式输出。

**里程碑指标**（上线反馈埋点后才能测，见 §7 决策点 5）：
- 答案 👍 比例
- 首次点击引用的比例（即"答案把人带到了文件"）
- 追问率（第二轮提问占比）

### 阶段 2 · 治治理（约 2–3 周，8–12 人日）

近似重复与版本差异 → 批量归类与规范命名 → OCR 策略校正 → 队列与后台状态可见 → 告警通道 → 涉密与业务标签体系。

### 阶段 3 · 协作与自动化（约 4 周+）

收藏/最近打开 → 评论 @ 与订阅 → 人工校正闭环 → 平台内 agent 代办 → 自动简报推送。

### 依赖关系（重要）

```
阶段 0（反馈埋点 + 修数据 + 补安全口子）
   ├─► 阶段 1（按反馈数据决定重排/改写的力度）
   └─► 阶段 2 的基础（台账干净了才谈得上治理）
                    │
阶段 2（治理 + 目录先验） ──► 阶段 3（协作 / agent / 人工校正闭环）
```

**结论：阶段 0 不能跳。** 跳过它做阶段 1，等于闭着眼睛调检索。

**三条"如果不做的后果"**

1. 不做反馈与重排 → 问答继续"看起来能用、实际不准"，用户默默回到微信问人，**平台沦为第二个文件浏览器**。
2. 不做备份与告警 → 某次索引损坏或 NAS 抖动，需要重跑数小时解析且无人知晓；**已在 10-24 / 10-25 两次事故里验证过这个风险**。
3. 不治台账与重复 → 文件越堆越多、越堆越乱；**≈20 万文件的整理是人做不完的**，最终平台会因为"找不到"而废弃。

**风险清单（来自实测）**

| 风险 | 现状 | 缓解 |
|---|---|---|
| SQLite 单写争锁 | 流水线日志持续 `database is locked` | 批处理挪低峰 / 独立连接 |
| WAL 膨胀 | WAL 2.49 GB > 主库 2.25 GB | 排查长读事务；备份用备份 API |
| NAS 带宽 | MD5 哈希 128 个文件 6 秒（约 21 文件/秒）；OCR 136 秒/页 | 分级队列 + 限额 |
| 队列不可见 | 572 个 extract 任务静默排队 | 阶段 0 补状态接口 |
| 索引可重建性 | 可从 NAS 重建，但**无重建脚本** | 阶段 0 顺手写运行手册 |
| 双重实现 | 两套授权 / 两套流水线 / 两套统计并存 | 阶段 2 末尾收敛到 grants + SourceScanner |
| 批量 LLM 抢占 | 摘要/差异比对会与 Tier2 积压抢算力 | 只走算力池、本地+远端、不用云端；批量任务有进度可见 |

## 7. 需要拍板的 6 个决策点

1. **索引范围**：目前只有 `信息化管理\AI知识库` 被解析（677 篇），其余 4 个共享（约 20 万非文档文件）只可浏览。**要不要放开？** 建议按业务价值分批放开，而不是一次全开。**前提：涉密标记的管理台入口（阶段 0/B5）必须先落地**——已标的 8 个涉密目录一旦进入索引范围就会自动生效（改走本地模型、禁下载），标错了会静默降级答案质量。
2. **涉密的 8 个标记是否属实？** 需要业务负责人确认；并补一条回归测试（今天这条路径在生产里从未被触发过）。
3. **embedding 的修法深度**：阶段 0 只做"按块嵌入 + 救回 4 篇"（不动全局块长，1 人日，无副作用）；**全局重切块（≈2,800 → ≈1,000 字符）会让全部 1,530 个块失效，需要一次维护窗口并重跑 Tier2**（代价：Tier2 要重新排队，与当前积压叠加）。是否安排这个窗口？
4. **平台自己的 wiki 导出放哪？** 现在导出到被监控的 NAS 根目录（`AI知识库\_kb\`），是 113 条脏目录行 + 20% 无效队列的来源。建议**搬离监控根**（改到 `kb/data/wiki`），NAS 上的 `_kb` 目录在确认后清掉；同时注意"人工可编辑的 wiki"目前落在 NAS 上，搬走后需要一个替代方案。
5. **反馈只收 Web，还是飞书也收？** 飞书是移动端主入口且链路最成熟；如果反馈只在 Web 收，阶段 1 的里程碑指标样本会很小，"阶段 0 不能跳"的前提就站不住。建议**两处都收**，飞书侧识别"这条不对"意图作为独立任务项。
6. **重复件清理要不要我代劳？** 现在有 17 组 / 44 份 / 74.2 MB 待处理（删除进回收站可恢复）。建议先在界面上人工过一眼再批量执行。

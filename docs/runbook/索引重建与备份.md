# Runbook：索引重建与备份

适用：企业知识平台 2.0（`D:\kb-platform`，branch master）。
索引的三个组成部分：`kb/data/kb.db`（平台库+引擎库，SQLite WAL）、
`kb/data/fts.db`（FTS5 全文索引）、`kb/data/vectors/`（fp16 向量）。
用户的原文件永远只在 NAS 上，索引坏了可以整体重建，不必慌。

---

## 1. 备份

### 1.1 备份在哪

- 目录：`D:\kb-platform\kb\backups\`（**本地盘**，特意不放在被监控的
  NAS 根目录下——否则备份文件会被平台自己扫进索引，Task 0.1 刚修过这类自吞问题）。
- 一次备份 = 同一时间戳的 4 个文件，恢复时**必须配对使用**：

| 文件 | 内容 | 生成方式 |
|---|---|---|
| `kb-YYYYMMDD-HHMM.db` | kb.db 整库快照 | SQLite backup API |
| `fts-YYYYMMDD-HHMM.db` | fts.db 快照 | SQLite backup API |
| `vectors-YYYYMMDD-HHMM.f16` | 向量矩阵 | 文件复制（非 SQLite） |
| `vectors-YYYYMMDD-HHMM.ids.json` | 行序→chunk_id 对照 | 文件复制（非 SQLite） |

- 保留最近 **7** 份（每天 1 份 ≈ 2.6 GB × 7 ≈ 18 GB，本地盘余量充足）。
- 计划任务 `OpenCode-KB-Backup`：每天 02:00 触发，失败重试 3 次（间隔 5 分钟）。
  日志：`kb\logs\backup.log`。

### 1.2 为什么必须用 SQLite 备份 API（不要复制 kb.db）

kb.db 是 WAL 模式：已提交但还没 checkpoint 的事务躺在 `kb.db-wal` 里
（2026-10-25 实测 WAL 曾到 **2.49 GB**，比主库还大，见 §3）。直接复制 kb.db
会漏掉这些事务，产物不是任何时刻的一致性快照，多半恢复不了。
`python -m kbplatform.backup` 用 `sqlite3.Connection.backup()` 在线逐页拷贝，
对源库只读、不删不改生产数据，边有写入也能出一致快照。

### 1.3 手工触发一次

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File D:\kb-platform\tools\backup-db.ps1
# 改目录 / 改保留份数：
powershell -NoProfile -ExecutionPolicy Bypass -File D:\kb-platform\tools\backup-db.ps1 -Dest D:\some-dir -Keep 14
```

或直接调 Python（`-Dest` 不传时默认 `kb\backups`）：

```powershell
& $env:LOCALAPPDATA\Programs\Python\Python312\python.exe -m kbplatform.backup --config D:\kb-platform\config.toml --keep 7
```

**预计耗时（实测生产库）**：kb.db 2.25 GB + fts.db 170 MB + vectors 55 MB
**8.2 秒**（2026-10-25，平台运行中）。备份后可用 `PRAGMA quick_check`
验证快照可用（实测 2.2 GB 快照 8.0 秒返回 ok）。

安全闸门：备份目录若落在 `config.toml` 的监控根之下，CLI 会直接报错退出（exit=2）。

## 2. 从备份恢复（索引损坏 / 误删时）

1. **先停平台**（否则流水线一边写一边换文件，恢复必坏）：

   ```powershell
   Stop-ScheduledTask -TaskName OpenCode-KB-Watchdog   # 先停看门狗，否则它每分钟把平台拉回来
   Stop-ScheduledTask -TaskName OpenCode-KB-Platform
   Stop-Process -Name pythonw -Force -ErrorAction SilentlyContinue
   ```

2. 选最新一份时间戳齐全的备份（4 个文件都在）：

   ```powershell
   Get-ChildItem D:\kb-platform\kb\backups
   ```

3. 用快照覆盖现场（把 `<ts>` 换成所选时间戳）：

   ```powershell
   $ts = "20261025-2108"
   $data = "D:\kb-platform\kb\data"
   # 旧库三件套 + 其附属文件全部移走（留作事故现场），不要只删 kb.db
   Move-Item "$data\kb.db","$data\kb.db-wal","$data\kb.db-shm","$data\fts.db" "$data\broken-$(Get-Date -fyyyyMMdd-HHmmss)\" -Force
   Copy-Item "D:\kb-platform\kb\backups\kb-$ts.db"      "$data\kb.db"
   Copy-Item "D:\kb-platform\kb\backups\fts-$ts.db"     "$data\fts.db"
   Copy-Item "D:\kb-platform\kb\backups\vectors-$ts.f16"      "$data\vectors\vectors.f16" -Force
   Copy-Item "D:\kb-platform\kb\backups\vectors-$ts.ids.json" "$data\vectors\vectors.ids.json" -Force
   ```

   注意：**不要把旧的 kb.db-wal / kb.db-shm 留在现场**，它们和恢复出的主库不配对。

4. 验证快照能打开：

   ```powershell
   & $env:LOCALAPPDATA\Programs\Python\Python312\python.exe -c "import sqlite3; c=sqlite3.connect(r'D:/kb-platform/kb/data/kb.db'); print(c.execute('PRAGMA quick_check').fetchone()); print('catalog:', c.execute('SELECT count(*) FROM catalog').fetchone()); c.close()"
   ```

5. 重新拉起平台：

   ```powershell
   Start-ScheduledTask -TaskName OpenCode-KB-Platform
   Start-ScheduledTask -TaskName OpenCode-KB-Watchdog
   Invoke-WebRequest http://127.0.0.1:8000/health -UseBasicParsing
   ```

回滚代价 = 备份时刻到现在的增量：备份之后新上传的文档会回到 pending，
下一轮流水线自动重新索引；已入库文档在监控快照里不会重复跑。

## 3. WAL 排查记录（2026-10-25，W1）

现状测量（处理前）：

| 文件 | 大小 |
|---|---|
| `kb.db` | 2,355,814,400 B（2.19 GiB） |
| `kb.db-wal` | 2,609,649,232 B（2.43 GiB，**比主库大**） |
| `fts.db` | 178,696,192 B（170 MiB） |

处置与结果：

1. `PRAGMA wal_checkpoint(PASSIVE)` → `(0, 117, 117)`：没有阻塞的读者，
   待拷贝帧只有 117 页——WAL 里绝大部分是**已 checkpoint 过的死帧**
   （journal_size_limit 默认 0，checkpoint 后文件从不收缩，只往前追加、
   文件越积越大）。
2. `PRAGMA wal_checkpoint(TRUNCATE)` → `(0, 0, 0)` 一次成功，
   `kb.db-wal` **2.49 GB → 0**。说明当时没有长读事务占着（排查结论：
   不需要动其它 pragma，也不存在饥饿的写者；文件膨胀是"死帧从不回收"积累的，
   不是当下有事务卡住）。
3. **固化 `PRAGMA journal_size_limit=268435456`（256 MB）** 到
   `kbplatform/db.py` 的 `connect()`（必须在 `journal_mode=WAL` **之后**设置，
   否则不生效），并加了断言测试
   （`kbplatform/tests/test_backup.py::test_connect_sets_wal_journal_size_limit`）。
   之后 WAL 即使再次积到 2 GB+，checkpoint 完成时文件也会被截回 ≤256 MB。
4. 处理后实测：`kb.db-wal` = 4,490,832 B（平台照常运行）。

**行为变更与风险说明**（pragma 属于影响全平台的行为变更）：
- 改了什么：打开连接时设置 `journal_size_limit=256MB`，不改任何锁行为、
  不改 journal_mode。
- 为什么：WAL 从不收缩导致磁盘被陆续吃掉 2.5 GB+；256 MB 上限即可容纳
  正常的 checkpoint 间隔增量（实测空闲时 4 MB）。
- 风险：上限是**文件级收缩**，被截掉的帧若尚未写入主库不可能被截
  （TRUNCATE checkpoint 必须先拷贝才能截）；断电恢复路径（WAL 回放）不变，
  不会丢已提交数据。若某次 TRUNCATE checkpoint 被读者挡住，文件只是暂时
  不收缩，下次成功时再缩，功能没有损失。

日常巡检命令（排障时用）：

```powershell
& $env:LOCALAPPDATA\Programs\Python\Python312\python.exe -c "import sqlite3; c=sqlite3.connect(r'D:/kb-platform/kb/data/kb.db', timeout=30); print(c.execute('PRAGMA wal_checkpoint(TRUNCATE)').fetchone()); print('wal_autocheckpoint:', c.execute('PRAGMA wal_autocheckpoint').fetchone()); print('journal_size_limit:', c.execute('PRAGMA journal_size_limit').fetchone()); c.close()"
```

观察点：`wal_checkpoint(TRUNCATE)` 的第二个/第三个值长期 >0 且不回落，
或 WAL 不再收缩 → 有长读事务/未关游标占着，先查 `pipeline` / 长跑脚本，
再考虑加码，不要上来就改锁相关 pragma。

### 3.1 事故：WAL 涨到 125 GB 写满磁盘（2026-11-17）

**现象**：整站离线。`http://192.0.2.203:8000` 拒绝连接；`web.err.log` 里
web 每次启动都死在 `db.init_db → _repair_chunk_fk` 的
`sqlite3.OperationalError: database is locked`（supervisor 重启了 41 次）；
`ingest.out.log` 刷 `database or disk is full`；`supervisor.err.log` 有
`OSError: [Errno 28] No space left on device`。D 盘 285.3 GB 只剩 0。

| 文件 | 故障时 | 处置后 |
|---|---|---|
| `kb.db` | 10.1 GB（mtime 停在 11/15 09:44） | 10.1 GB |
| `kb.db-wal` | **134,928,211,976 B（125.66 GB）** | 0 |
| D 盘可用 | 0 | 126.6 GB |

**根因**：`extract_runner._worker` 捕获异常后没有 `rollback()`。那条提炼线程
的连接从此停在旧事务里，它持有的读快照让 checkpoint 永远只能复制到快照
为止 → WAL 只追加不回收。`journal_size_limit` 只在 checkpoint **成功后**收缩
文件，拦不住这种增长（§3 的 256 MB 上限因此失效）。`kb.db` 从 11/15 09:44
起就没再被 checkpoint 过，两天堆出 125 GB。

**处置**：

1. `Disable-ScheduledTask OpenCode-KB-Watchdog / OpenCode-KB-Platform`，
   再杀掉 supervisor 及其 web / pipeline 子进程（否则看门狗每分钟把写者拉回来，
   checkpoint 必然 `database is locked`）。
2. 留出写回空间：把 11/10、11/11 两套旧备份 `Move-Item` 到
   `U:\kb-backups-archive`（保留数据，不删除）。
3. 单连接执行 `PRAGMA wal_checkpoint(TRUNCATE)`。125 GB 的 WAL 首次打开
   要重建 `-shm` 索引，**实测扫描约 10 分钟**（CPU 持续占用、IO 计数为 0
   是正常的，不是卡死）；完成后返回 `(0, 0, 0)`，`kb.db-wal` 归零。
4. `PRAGMA quick_check` = `ok`（10 GB 库约 3 分钟），然后
   `Enable-ScheduledTask` + `Start-ScheduledTask` 两个任务，`/health` 200。

**防复发**（已落地）：

- `kbplatform/extract_runner.py`：异常分支先 `self.conn.rollback()` 再
  `queue.finish()`，并在 `pipeline.run_forever` 的失败分支同样回滚。
- `kbplatform/db.py::checkpoint_wal(conn, db_path)`：WAL 超过 4 GB 就
  `wal_checkpoint(TRUNCATE)`；抢不到锁只记日志、下轮重试，不阻塞业务。
  `pipeline.run_forever` 每轮结束调用一次。
- 回归测试：`test_backup.py::test_checkpoint_wal_truncates_oversized_wal`、
  `test_checkpoint_wal_leaves_small_wal_alone`。

**教训**：WAL 大小是必须盯的运行指标（管理台「运行状态」已有 WAL 大小）。
正常只有几十 MB；一旦超过 1 GB 就查长事务，不要等到磁盘写满——那时连
checkpoint 需要的空间都没有了。

## 4. 索引从 NAS 重建（kb.db / fts.db / vectors 全坏时）

用户的原文件都在 NAS 上，以下清掉的是**索引**，不动 NAS 文件。
全流程一口气跑完的话：**扫描 2–4 小时（量大时更久，QPS 限流 ~20 文件/秒）+
Tier1 解析 + OCR 若干小时 + Tier2 提炼随其后**。中途随时可以恢复服务 waiting。

先备一次份（§1.3）——这是唯一能退回去的现场。

1. **停平台**（同 §2 第 1 步：先 Watchdog 再 Platform，进程也杀干净）。

2. **清索引表**（不删 NAS 文件；`fs_entries` 是 2.0 文件底座的路径表，
   由存储源扫描自己维护，**不清**）：

   ```powershell
   & $env:LOCALAPPDATA\Programs\Python\Python312\python.exe -c "import sqlite3; c=sqlite3.connect(r'D:/kb-platform/kb/data/kb.db'); c.execute('PRAGMA foreign_keys=ON'); n=0; [n := n + (c.execute('DELETE FROM ' + t).rowcount or 0) for t in ('catalog','catalog_stats','chunks','jobs','knowledge','nodes','edges')]; c.commit(); print('deleted rows total:', n); c.close()"
   ```

   清空各表行数会打印出来，量大时 catalog DELETE 可能要几分钟。

3. **重置向量库**（fp16 文件按行追加，行序对应 chunk_id，主库清了必须重建）：

   ```powershell
   Move-Item "D:\kb-platform\kb\data\vectors\vectors.f16","D:\kb-platform\kb\data\vectors\vectors.ids.json" "D:\kb-platform\kb\data\vectors\stale-$(Get-Date -fyyyyMMdd-HHmmss)\" -Force
   ```

   （`_load_ids` 找不到 ids 文件会自动从空开始，不用手工建空文件。）

4. **重启平台**，监控会重新全量扫描 NAS（`upsert_catalog` 幂等）：

   ```powershell
   Start-ScheduledTask -TaskName OpenCode-KB-Platform
   Start-ScheduledTask -TaskName OpenCode-KB-Watchdog
   ```

   每轮 `pipeline.run_once`：先扫描写 catalog → 变更检测 → 入队 index →
   Tier1 索引（解析/OCR/分块/向量/FTS upsert）→ 每篇索引成功自动入队
   extract → Tier2 提炼（走解析算力池）。**不需要单独的"重建 FTS"命令**：
   `indexer.index_file` 会顺带写 `fts.db`（upsert）和向量文件；
   `kb.db-wal` 走完流水线后同样受 journal_size_limit 约束。

5. **可选：只重建 FTS、跳过重解析**（chunks 还在、只怀疑 fts.db 坏）：

   ```powershell
   & $env:LOCALAPPDATA\Programs\Python\Python312\python.exe -c "from kbplatform import fts; from kbplatform.db import connect; c=connect(r'D:/kb-platform/kb/data/kb.db'); rows=c.execute('SELECT id, text FROM chunks').fetchall(); fts.build_index(r'D:/kb-platform/kb/data/fts.db', rows); print('rebuilt chunks:', len(rows)); c.close()"
   ```

   预计耗时：1530 chunks 实测秒级；几万 chunk 也就是几分钟。

**预计耗时参照（本轮生产数据）**：catalog 564 行 / chunks 1530 行量级下，
单轮扫描分钟级、Tier1 视文档体积常数分钟到小时级（含 OCR 扫描件一页 ~136s）、
Tier2 走算力池与文档大小/池权重相关。历史经验：整个 NAS 全量重扫 + 全解析
在 2–4 小时量级，上面的顺序跑完即与全新建库等价。

**收尾检查**：`Invoke-WebRequest http://127.0.0.1:8000/health`；
看 `kb\logs\supervisor.*.log` 里 `stats={"indexed":…}` 递增；
`GET /api/v1/board` 的 tier1/tier2 计数应逐步回升到 NAS 文件总数。
